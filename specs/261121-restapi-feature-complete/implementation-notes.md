## M4-F and M4-G decisions (worker w4, `m4/w4`)

- Bundle: `domain.Bundle` carries `schemaVersion` (14, the -db schema), teams and agents as column allowlisted rows, and a SHA-256 over its canonical JSON (sorted keys, no whitespace). `ParseBundle` rejects a checksum mismatch, an unknown shape, a schema version it does not know, duplicate team slugs and any key that looks like a secret value, key hash or client secret.
- Export build: the reconciler claims one pending row with `FOR UPDATE SKIP LOCKED`, reads the team state, writes the object through the `export.Blob` port (`Put`, `PresignGet`) and records `s3_uri`, `sha256`, `size_bytes`, `download_url` (7 days) and `succeeded`; a failure records `failed` with a summary and no checksum. ASSUMPTION for the integrator: M4-E4 supplies the `Blob` implementation (S3 with KMS, env `AFS_EXPORT_BUCKET`, `AFS_EXPORT_KMS_KEY_ID`); `cmd/afs-reconciler/wire_export.go` `exportBlob()` returns nil until it is plugged in, and the job stays unregistered. afs-api makes no S3 call (archtest `TestAPIBinaryClients`).
- Import: dry run is the default (`dryRun=false` applies). Each team runs in its own savepoint, so a failing team writes nothing and is reported while the others apply. Rows are written with `jsonb_populate_record` through the same column allowlists as the export. Role links import as `pending_trust`. The account map rewrites allowed accounts, secret ARNs, identity references and role links; a missing account is a validation failure for that team. Secrets are created as metadata only and reported as needing a value.
- Idempotency for import and restore uses `acting.Idem` in the first transaction; the per-team work is inside it.
- Restore: `RestoreRevision` locks the team row (`FOR UPDATE`) so concurrent mutations serialize, rebuilds the target state from `config_revisions` (newest revision of each resource with id <= rev, a delete means absent), plans with `domain.PlanRestore`, and applies each step in a savepoint. A step refused by a DB guard (pg classes 22, 23, P0001, 55000, 42501) is skipped and reported. A dry run runs the same steps and rolls back. `generation` goes up by one; one audit record names the revision.
- DB gap X-DB-8: `agent_secret_bindings` has no revision trigger, so restore cannot rebuild secret bindings and leaves them alone. A -db change is needed to restore them.

## M5-E and M5-F decisions (worker w3, `m5/w3`)

- **Viewer kubectl, OQ-9 default kept.** No access entry is made without a configured federated role. The roles come from `AFS_VIEWER_KUBECTL_ROLES` because the schema has no column for them.
- **One access entry per federated role, not per team.** EKS has one access entry per principal per cluster, so each role gets a single entry mapped to a role-specific Kubernetes group with no access policy; a namespace RoleBinding per team grants that group the read-only `afs-viewer` Role. Removal is binding first, then the entry once no team uses the role. Only entries tagged `afs-managed-by=viewer-kubectl` and Roles AFS created are ever changed.
- **Kubeconfig carries no token.** The YAML uses the `aws eks get-token` exec plugin; the cluster comes from `AFS_CLUSTER_NAME`, `AFS_CLUSTER_ENDPOINT`, `AFS_CLUSTER_CA_DATA` and `AFS_AWS_REGION` (OQ-S5), and the API answers `503` while they are unset.
- **Cost tag evidence comes from `cost_daily`.** "Seen in the CUR" is derived from the CUR rows `cur-ingest` stored (a key in the row's tag set; the agent and pool columns for `afs-agent-id` and `afs-pool-id`; any CUR row for `afs-team-id`), so no second Athena query is needed and the status agrees with the reports.
- **`cost_tags.not_seen` once per activation, without a separate marker table.** `afs_billing` cannot write audit rows or read `service_settings`, so the check derives "already raised" from the stored row (its `checked_at` and AWS status) and the activation time AWS reports now: overdue now and not overdue at the previous run raises the event. A rerun, or the next day, raises none; deactivating and activating again starts a new period. When Cost Explorer fails, the AWS status is kept and the job fails visibly.
- **Not done:** no drift-watch `OwnedKinds` entry for the viewer Role and RoleBinding; the `[e2e]` case for viewer kubectl compiles but runs only on the dev cluster in M6-F.
## M5-C and M5-D decisions (worker w2, `m5/w2`)

- **Pool names.** The Deployment and ServiceAccount are `pool-<name>`, so `resolve_workload` (SA name) and the pod labels (`LabelPoolID`) identify the pool; the pool role is `afs-<pool ulid>` under the team's role path; the egress policy is `afs-egress-<pool id>`, labelled `resource-kind=pool` so the agent egress prune never lists it.
- **Replicas come from desired state.** `Desired.Replicas()` is the row's `workers`, or 0 when the pool is paused or the team is suspended; there is no prior-state store for pools because the row keeps the count. A pause or suspend never changes the pod-template hash.
- **Conditions beyond the contract** (the list is open): `WorkersReady`, `InboxReady`, `RoleLinksVerified`, plus `IamReady`, `TagsApplied`, `SecretsSynced`, `EgressPolicyReady`, `TemplateRetired`.
- **Inbox queues.** Name `afs-<team ulid>-<sha256(pool id)[:8]>`, so it is deterministic and unique per pool. The resource policy allows on the account root narrowed by `aws:PrincipalArn` (a role that does not exist yet does not invalidate the policy) and denies everyone else on send, receive, delete, change visibility and purge. The reconciler administers the queue (create, set attributes, tag, delete), which the denies do not cover. The permissions boundary of the team roles must allow `sqs:*` actions on `afs-*` queues only for receive/send as the pool role statements grant (deploy/terraform follow-up, not in this stream's paths).
- **Role link probe.** The pool probe reuses `links.Probe` with the pool id as agent id and session name, so the session tag is `afs-agent-id=<pool id>`; the pool role trusts `AFS_RECONCILER_ROLE_ARN` like a dedicated agent role.
- **Shared EFS claim.** RWX on `AFS_EFS_STORAGE_CLASS` (default `efs-sc`), nominal 1Gi; removed when `shared_volume` goes to `none`. The scratch volume is a generic ephemeral volume, deleted with its pod.
- **Drift.** `k8s.PoolOwnedKinds()` adds the Deployment to the watcher; the `deployment.kubernetes.io/revision` annotation causes a drift event that reconciles to a no-op.
- **Teardown completion marker.** `torn_down_at` is set to the database `now()` when the teardown starts (the `teams_teardown_recorded` check wants it with the reason) and set equal to `deleted_at` when the record is closed. A deleted team with `torn_down_at < deleted_at` has not been closed, so the sweep does not read the outbox (whose rows are purged). Reasons are the contract's `expired`, `cap_reached`, `work_complete`; `manual` belongs to the API's delete path.
- **Wrapper completer not used.** After the finalizer's Complete the team is `deleted` and no longer reconciles, so the closing record is a separate sweep in the same job.
- **First apply of a PVC.** The API server touches a new claim's managed fields once more on the apply after its creation, so the no-op assertion in envtest is on the third pass.
